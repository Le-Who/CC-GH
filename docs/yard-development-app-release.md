# CC-GH development protocol release

This is a new development route for the reviewed Yard storage/protocol evolution on games.tri.mom. It does not alter initial activation or compatible maintenance rules. It does not authorize a deployment, create a release request, or constitute image acceptance by itself.

The current predecessor is exactly `6b80c9a2cca146e20afcaced6a34a035c30c13aa`, tree `11d0b3664a6657383d4011720e598ff901006f84`. A different predecessor requires a newly reviewed evolution of this contract. Current accepted-active receipts remain the source of predecessor image digest, local image ID, and accepted/deployed provenance.

## Storage limitation accepted for development

The candidate reads Yard storage versions 1 and 2. A successful canonical placement first writes version 2; picking the item up does not downgrade it. The old app can quarantine a version-2 Yard as unsupported while preserving its bytes. Therefore an application rollback can restore the old service and authentication while leaving migrated Yard gameplay read-only. It must not be reported as a compatible gameplay rollback.

The user has explicitly waived old-save compatibility for this development rollout. There is no reader bridge, reset, database restore, destructive migration, or automatic downgrade in this route. A future launch-time reset is a separate action. Current-format integrity, normal account ownership, pending intent fences, receipt security, and exactly-once actions remain required.

## Source and image acceptance, before preparing a host packet

The coordinator must land the selected product delta on the current predecessor, preserve its 24 live-only paths, and apply the separately reviewed capability and food corrections. Do not replace the branch with the older candidate. The final source closure must explicitly enumerate source, build, test, and release-tool changes, including intentional updates to historical frozen-source checks. Do not silently exempt this candidate from maintenance or standard CI protections.

Build one normal production image from that exact final commit/tree. The reproducible image path must pass the reviewed optional client-graph build argument to Vite. The value must be explicit in the image-producing workflow; ordinary URL parameters cannot add omitted build assets. Do not rebuild after acceptance. Bind the OCI revision label, immutable registry digest, local image ID, backend build ID, and served client build.

The server capability policy must be source owned and consistently applied to normal authenticated initialization, mutation, and snapshots. The accepted scope is at most two `leaf_pot` placements, place/move/pickup, normal inventory/economy, existing food purchase actions, and `bowl-1` food presentation. Canonical visitor admission remains off. CI fixture loaders, test preloads, client/query/local-storage capability authority, fake accounts/responses, and dev-auth relaxation must not run in the deployed image. Keep `NODE_ENV=production` and `DEV_AUTH_ENABLED=false`.

Normal-image CI proves those runtime properties only for the environment exercised by CI. The VPS inherits its existing `.env` and Compose environment; that is a separate, currently unimplemented host-preflight gate. Before host use, a trusted read-only preflight must establish the actual effective app environment and proposed candidate configuration, emitting only `nodeEnvProduction`, `devAuthDisabled`, and `nodePreloadAbsent` booleans. Require all three to be true: production mode; dev auth absent or explicitly disabled; and no Node preload influence from `NODE_OPTIONS` or effective startup/entrypoint arguments. Fail closed on nonempty `NODE_OPTIONS`, preload/loader arguments, unknown values, or unavailable proof. Evaluate any needed values locally in memory; never print, log, upload, or persist environment values, command lines, credentials, or a full environment dump, and do not change the environment to make the check pass. The current helper does not compute these booleans. Its `/api/config` auth checks, Compose hash comparisons, and the verifier container's cleared `NODE_OPTIONS` do not substitute for proof of the actual app environment.

An independently trusted CI/controller adapter must obtain and verify successful workflow/artifact provenance for the exact image and source. Use the existing authoritative accepted-image/receipt mechanism where applicable; do not call `assertMaintenanceChecks` or `verifyMaintenanceRollback` for this transition because their same-format premise is false. The new development adapter must produce the `cc-gh-yard-accepted-development/v1` receipt consumed by the guard. It must prove each check listed by `CHECKS` against the exact final image and predecessor, including normal authenticated capabilities, placement storage, inventory/economy, lost-response replay, pending/account fences, receipt security, occupied food socket, warm client update, mobile functional/visual checks, app-only failure handling, and byte-preserving old-image quarantine. One check name or a self-authored `success` JSON value is not evidence. The offline guard validates binding and completeness, not GitHub authenticity.

This source overlay deliberately supplies no made-up real candidate commit, image digest, accepted receipt, or deploy authorization. The coordinator owns the acceptance workflow and selection of its complete test/QA closure. A real host packet cannot be prepared until those artifacts exist and are independently verified.

## Packet and independent approval

The private packet directory contains only these non-secret files:

- `development-record.json`: the exact reviewed `cc-gh-yard-development-release/v1` record
- `predecessor-receipt.json`: authoritative `cc-gh-yard-accepted-active/v1` receipt bytes
- `candidate-receipt.json`: authoritative `cc-gh-yard-accepted-development/v1` receipt bytes

The approved record SHA-256 must come from the independently reviewed release request/controller, never from the candidate or a default computed on the host. The record pins both receipt byte hashes, both source/image identities, the explicit storage limitation and capability scope, the currently effective compose SHA-256, observed loopback port, games.tri.mom, existing database identifiers, and observed protected services. Database names/user identifiers are not credentials. Do not add `.env`, credentials, backup bytes, or player rows to this packet.

The shell takes five arguments: packet directory, independently approved record hash, existing CC-GH release root, authoritative prior image ID, and authoritative prior image digest. The release root is hardcoded as `/opt/game-hub`, checked against its physical path before any writable open; no environment flag or caller waiver can choose another root. The packet must be physically staged beneath its existing `releases/` directory, and the invoked shell/verifier must also be physical files beneath the approved root. Root, backups, compose, environment, lock, packet and verifier symlink redirection is refused. Regular file inputs must have one hard link. The exact prior image/digest must come from the authoritative receipt/controller, not from whatever container happens to be running.

The shell bootstraps its Node verifier from the independently pinned predecessor image. It uses bounded, network-disabled, read-only ephemeral verifier containers, explicit Node entrypoint, cleared preload options, and mounts only the verifier, each of the three secret-free packet files, compose file, and private evidence directory. It never installs host Node or any other tool. It requires existing Docker Compose v2, curl, timeout, flock, systemctl, and ordinary shell/coreutils. Availability and actual Caddy service inventory still need host-side read-only verification before use. Every Docker operation must use the default local Unix socket; remote contexts or ambient endpoint/config-directory overrides stop the helper before replacement. Curl configuration files and proxy routing are disabled for all fixed-origin health probes.

## App-only switch and rollback

The helper requires the existing regular, single-link `.release.lock`, opens it read-only, compares the opened descriptor's device/inode with the checked path, then acquires `flock` and rechecks the identity. It never truncates or creates a lock target and holds the same lock through any rollback. It preserves the effective compose and `.env` files. Its generated compose override has only the app image and `APP_BUILD_ID`; other app settings, all ports, networks, volumes, PostgreSQL, and Redis remain described by the unchanged files. Compose receives a clean invocation environment so caller variables cannot silently override those settings; the existing non-secret `GHCR_REPO=le-who/cc-gh` export is supplied explicitly. Environment file identity/metadata is checked without reading or printing its contents. [Compose's service hash](https://docs.docker.com/reference/cli/docker/compose/config/) is compared against the current app container's config-hash label before replacement and against each selected override after forward/rollback. Compose resolves secrets internally and prints only the digest. An unavailable/mismatching hash stops the operation; do not install or weaken a check to proceed.

Both directions use exactly `docker compose -p ccgh up -d --no-deps app`. The helper never invokes project-wide up, orphan cleanup, stale-name deletion, image/system/volume prune, host installation, Caddy mutation, DNS/provisioning, or host reboot. The candidate image must already be present locally. It performs no pull, registry login, build, publish, SSH, or asset upload.

Before replacement, it verifies the exact running predecessor and both immutable image identities, requires local/public health and build/config/HTML agreement, snapshots every other container plus observed services and host/Caddy start identity, creates a private local PostgreSQL archive, checks its archive catalog, hashes it, and retains a CC-GH-local prior-image tag. The archive and digest evidence are retained with read-only owner permissions. Backup bytes never enter the verifier mounts or leave the host. Immediately before the app-only switch, it rechecks predecessor health/settings/protected identities and the preserved backup's regular-file identity, permissions and exact digest against the already checked in-memory value. A corrupt/replaced archive or sidecar blocks the switch.

A definite command/health failure after replacement begins triggers one app-only rollback. The rollback is successful only after exact predecessor image/build identity and local/public health, PostgreSQL/Redis status, auth/config, HTML identity, and protected process identities pass. A running old container alone is not recovery. Failure or inability to prove rollback returns exit 70 and explicitly records the unverified state. A Compose CLI timeout or interruption does not prove that the Docker daemon cancelled the operation: that outcome stays unverified, no competing replacement is launched, and operator inspection is required before another switch. The backup is retained on success and failure; there is no automatic restore or deletion.

Immediately before replacement, the helper exclusively creates the private `/opt/game-hub/.yard-development-inflight` marker with exact candidate/predecessor identity and the evidence path. It clears only its own unchanged marker after a known completed operation and verified candidate success or verified predecessor rollback. Timeout, interruption, failed rollback, or a killed helper leaves this durable interlock in place. Every later helper invocation checks for it under the shared lock and exits before any Docker operation, even if a stale predecessor still appears healthy. There is no automatic age-based cleanup or override flag. Deliberate real-host reconciliation must establish that no daemon replacement remains pending, identify the actual app/image and healthy settings, inspect the retained evidence/backup, and explicitly resolve the marker before another release. The trusted controller and operators must honor this interlock across every CC-GH release path; an old workflow is not a bypass for an unresolved development operation.

All non-app containers are covered, including CC-GH PostgreSQL/Redis. Services are observed with read-only `systemctl show` fields; host boot ID and Caddy PID/start identity are compared. This detects process/container changes but cannot prove an unknown neighboring web application's end-to-end health. The record and result always say `neighbor-application-health-not-proven`. Add any broader health claim only from separately obtained known-route evidence.

Operational stderr after the private evidence directory is created is retained there, including errors from Docker, Compose and systemctl. Public output emits fixed outcome messages and the evidence location, never raw neighbor errors or assertion diffs. Do not publish that private operational log or inventory as a public CI artifact.

The exact accepted image is already built with its client assets. The source compose and `.env` are intentionally left untouched, and the selected override persists in the private evidence directory. The final receipt must preserve that path and mode so future CC-GH operations continue from the actual development image. Existing maintenance workflows will fail their predecessor/storage gates for this image; do not work around that by presenting it as same-format maintenance. A default manual Compose invocation without the persisted override could select the prior image and must not be used as the subsequent development release path.

The app's actual ports, mounts, network membership/mode, and restart policy are also captured from narrowly selected non-secret inspect fields and compared after each replacement. This catches runtime differences, including a manually attached network, that a Compose config-hash label alone cannot establish. Container IDs and dynamically assigned container addresses are intentionally not treated as stable app identity across recreation.

## Local verification scope

Run `node --test tests/yard-development-release.test.mjs` and `bash -n scripts/ccgh-app-development-release.sh`. The test suite supplies fake Docker/curl/systemctl/sleep executables and local packet fixtures. To exercise the production shell without touching `/opt/game-hub`, the test harness replaces exactly its one hardcoded root constant in a disposable copy; the production source has no runtime test flag or alternative-root waiver. The unmodified script is also tested to reject an arbitrary root before any write. The actual contract verifier runs inside the fakes as a Node child, so malformed packets and health/provenance mismatches exercise the real validation code. No Docker daemon, network request, live server, image build, or deployment is used.

Mocked tests establish command scope and failure behavior. They do not establish real Compose merge semantics, actual host tools, live image/receipt provenance, current neighbor identities, actual backup restorability, authenticated gameplay, or production visual quality. Those remain distinct gates for the coordinator's exact final candidate and host review.
